## Anti-Patterns Verdict

The interface does not read as generic AI SaaS. The custom ShelfLife mark, restrained teal/coral palette, warm paper surfaces, and circulation-desk language create an appropriate academic-library character. It avoids gradient text, glass cards, hero metrics, and identical marketing-card grids.

The deterministic `impeccable detect --json frontend/src` scan could not run because the local `npx` launcher is broken and no installed `impeccable` CLI was available. The live detector also could not initialize because its `.impeccable/live/config.json` configuration is absent. A source-based static check was completed instead: it found no banned gradient-text or colored side-stripe patterns; it did identify custom-dialog and form-label hotspots in BookListPage and MembersPage.

Live review covered login, catalog, loan issuance, custom dropdown behavior, member directory, and member-registration modal. Browser overlays were not available because the live detector server could not start.

## Overall Impression

ShelfLife now feels welcoming and purposeful rather than like a default admin template. The largest gap is not visual style. It is interaction robustness: the app’s custom controls and modals need the same care that was given to the visual system.

## What’s Working

1. The catalog makes its primary task clear: search, narrow by genre, then inspect availability. The page hierarchy leads directly to that workflow.
2. The issue flow communicates loan duration and due date before submission, while unavailable titles are visibly labelled and disabled.
3. Navigation uses familiar patterns with text labels, active states, and a responsive alternative to the desktop sidebar.

## Priority Issues

### [P1] Modal forms are not fully accessible or reliably escapable

**What:** The Add Book and Register Member dialogs do not associate labels with inputs, move focus into the dialog, trap focus, restore it on close, or close on Escape. Their close button is announced only as “✕”.

**Why it matters:** A keyboard or screen-reader user can lose context or interact with content behind the dialog. This fails the stated WCAG AA baseline during key administrative actions.

**Fix:** Give each control a unique `id` and each label a matching `htmlFor`; use `role="dialog"`, `aria-modal`, and `aria-labelledby`; move focus to the first field, trap Tab within the dialog, restore focus to the trigger, and make Escape and the backdrop close it when no submission is in progress. Give the close button `aria-label="Close dialog"`.

**Suggested command:** `impeccable harden frontend/src/pages`

### [P1] The custom Select is visually improved but incomplete as a combobox

**What:** The dropdown search field has no programmatic label, active options are not exposed through `aria-activedescendant`, and the menu does not present a clear way to reset an active genre filter to “All genres.”

**Why it matters:** Screen-reader users receive an ambiguous search field, and every catalog user must manually undo a filter or reload. The checkout control is too important for partial accessibility.

**Fix:** Use an accessible combobox pattern or a well-tested primitive. Add a labelled search input, a stable active-option id, `aria-activedescendant`, and a first “All genres / Clear selection” action where null is allowed. Announce result counts after filtering.

**Suggested command:** `impeccable harden frontend/src/components/common/Select.tsx`

### [P2] Member and history tables make mobile circulation work harder

**What:** Five-column tables rely on horizontal scrolling at narrow widths, with no visible scroll cue or compact mobile representation.

**Why it matters:** Names, status, and the next action can land off-screen, forcing lateral scanning when a staff member needs a quick answer.

**Fix:** Retain the table on desktop but switch to a compact stacked record pattern below a breakpoint. Keep name, availability/status, and the primary action visible first; move ISBN, joined date, and email into supporting rows.

**Suggested command:** `impeccable adapt frontend/src/components/common/DataTable.tsx`

### [P2] Form validation is too generic for a high-confidence desk workflow

**What:** New-book and new-member forms depend on native validation and toasts. They do not keep specific error guidance next to the relevant field.

**Why it matters:** A librarian correcting an ISBN, duplicate email, or missing field has to infer what to fix, which interrupts a face-to-face service interaction.

**Fix:** Track field errors, set `aria-describedby` and `aria-invalid`, preserve form data, and place a short correction below each affected field. Keep the retryable global error for network failures only.

**Suggested command:** `impeccable harden frontend/src/pages`

### [P3] Loading and empty states do not yet teach the product

**What:** Tables show a generic spinner and “Retrieving records…”, while empty results give limited next-step guidance.

**Why it matters:** The empty and loading moments are part of first-time confidence. They are a missed opportunity to show what users can do next.

**Fix:** Use table-shaped skeleton rows during loads. For zero results, offer a clear action such as “Clear search” or “Register a member” when appropriate.

**Suggested command:** `impeccable onboard frontend/src/components/common/DataTable.tsx`

## Persona Red Flags

### Alex, power user

Alex can quickly search and select with the keyboard in the dropdown, but cannot clear a genre in one action, has no table shortcuts or bulk path, and must navigate separate history views for each member. This is acceptable for the assessment scope, but weak for a busy circulation desk.

### Sam, keyboard and screen-reader user

Sam encounters unlabeled modal text fields, a close button called only “✕”, and a custom listbox whose focused active option is not programmatically announced. The primary create-member and add-book tasks therefore need remediation before the UI can claim WCAG AA readiness.

### Jordan, first-time librarian

Jordan understands the catalog and checkout language, but has no contextual explanation of what happens after issuing a loan, what makes a book unavailable, or how to recover from a field-specific error. The first successful toast is reassuring; the first validation failure is not.

## Minor Observations

- The large serif headings work as a brand accent, but should remain limited to headings and never be used for dense data or controls.
- The “Live inventory” sidebar card is attractive but informational rather than actionable. Consider making it an actual status indicator or remove it from a small workflow surface.
- The custom Select’s search is helpful for book titles but adds an extra level of interaction for the short genre list. A non-searching genre menu may be faster.

## Questions to Consider

1. Should “issue a loan” become the dominant first action for staff working at the circulation counter, instead of leaving catalog as the default landing page?
2. What does a librarian need to know immediately after issuing a book: only a toast, or a small printable or re-openable receipt with member, title, and due date?
3. Is “Live inventory” a real promise of a live data feed, or simply a design cue? If it is only decorative, does it earn its position?
